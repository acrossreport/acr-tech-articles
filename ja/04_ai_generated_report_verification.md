# AIが書いた帳票JSONを、印刷せずに安全に確定させる方法

## これは何の話か

「帳票のレイアウトをAIに書かせる」という使い方が増えています。ChatGPTやClaudeに
「この様式のJSONテンプレートを作って」と頼めば、それなりのものがすぐ返ってきます。

ただし業務で使うには、2つの壁があります。

1. **AIの出力は確率的**で、同じ指示でも毎回少し違う結果になりうる。見た目を確認せずに
   そのまま本番投入するのは危険
2. **プレビューと実際の印刷結果がずれるツールが多い**。結局プリンタで出して確かめる
   しかなく、AIに直させるたびに実機検証が発生してしまう

本記事では、筆者が開発している帳票エンジン ACR（Across Report）を使って、この2つを
どう解決しているかを、実際に動くコードとともに紹介します。

## 問題1: プレビューと印刷結果がずれると、AIとの反復が成立しない

AIに帳票のJSONを書かせて確認・修正を繰り返す場合、理想のループはこうです。

```
AIが定義を書く → プレビューで確認 → おかしければAIに直させる → 再プレビュー → 確定
```

ここで「プレビューと印刷結果が一致する」という前提が崩れると、このループは
成立しません。プレビューでは良さそうに見えても、実際に刷ると罫線がずれる・
バーコードが読み取れない、ということが起きれば、結局毎回プリンタで確認する
羽目になり、AIによる反復のメリットが消えてしまいます。

ACR は Google Skia で直接 PDF/PNG を描画するため、プレビュー（HTML/画面表示）と
最終出力（PDF）が同一の中間描画モデル（`RenderCommand`）を参照します。これにより
プレビューと印刷結果が実機なしで一致し、AIとの反復を実機なしで完結できます。

## 問題2: 確定したはずの定義が、後から改変されていないと言えるか

AIが書いた定義を人が確認し、「これでOK」と確定したとします。しかし、その後：

- そのJSONファイルが別の場所にコピーされ、気づかないうちに書き換えられていないか
- 本番環境でレンダリングしたとき、確認時と同じ結果が出ているか
- フォントやエンジンのバージョンが変わって、見た目が変わっていないか

を後から検証する手段がないと、「確認した」という事実に意味がなくなります。

### 実装: テンプレート・データ・描画結果のハッシュを記録する

ACR のネイティブエンジン（`acr_dll`、Rust製）に、`provenance` という opt-in の
Cargo フィーチャーを追加しました。有効化すると、既存の FFI 関数には一切手を
加えずに、新しい関数が2つ追加されます。

```rust
// Cargo.toml
[features]
provenance = ["acr_core/provenance"]
```

```bash
cargo build --release -p acr_dll --features provenance
```

```c
// 追加される C ABI（既存の acr_render_pdf 等はそのまま）
char* acr_compute_render_manifest(const char* template_json, const char* data_json);
void  acr_free_manifest_string(char* ptr);
```

`acr_compute_render_manifest` を呼ぶと、以下のような JSON が返ります。

```json
{
  "template_sha256": "4c0592dc635ba2dd9aea6379189a4b7845414b3496d5d367e4cb2c055a5b7516",
  "data_sha256": "bbc579eb2b157e56080fa61972a7a63054e323400a7ef731d0012948f19c32bc",
  "acr_version": "2.0.0",
  "render_sha256": "4f53cda18c2baa0c0354bb5f9a3ecbe5ed12ab4d8e11ba873c2f11161202b945",
  "fonts_sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
}
```

設計上のポイントは2つです。

**1. テンプレート/データのハッシュは、キー順や空白の違いを吸収する**

入力JSON文字列をそのままハッシュすると、キー順や空白が違うだけの同一内容の
JSONが別物として扱われてしまいます。そこで、一度 `serde_json::Value` に
パースしてから再シリアライズし、その結果をハッシュします（`serde_json` は
デフォルトでオブジェクトのキーを `BTreeMap` で保持するため、出力は常に
同じキー順になります）。

```rust
pub fn canonical_json_sha256(json_str: &str) -> Result<String> {
    let value: serde_json::Value = serde_json::from_str(json_str)?;
    let canonical = serde_json::to_vec(&value)?;
    Ok(sha256_hex(&canonical))
}
```

**2. 描画結果のハッシュは、最終PDFではなく中間描画命令（RenderCommand）に対して取る**

最終的な PDF バイト列は、作成日時の埋め込みや、OS・フォント環境によるラスタライズの
微細な違いで変わり得ます。これでは「入力が同じなら必ず同じ結果になる」という
再現性の検証に使えません。そこで、Skiaで描画する直前の中間描画命令（Rustの
`Vec<Vec<RenderCommand>>`）をハッシュ対象にしています。入力（テンプレート・データ）が
同じであれば、OSや実行タイミングによらず同じハッシュになります。

### 検証はどうやるか

エンジン側に「検証」専用の関数は用意していません。検証は呼び出し側で、
**保存しておいた manifest** と、**同じテンプレート・データで `acr_compute_render_manifest`
を呼び直した結果**を比較するだけで行えます。

- `template_sha256` だけ不一致 → 様式が差し替えられた
- `data_sha256` だけ不一致 → データの中身が変わった
- 入力は同じで `render_sha256` だけ不一致 → エンジンやフォント環境が変わった

### ウォーターマーク（ライセンス状態）の影響を受けない

`render_sha256` は、Skia で実際に描画する**前**の中間描画命令の段階でハッシュを
取っています。ウォーターマークの有無はこのあとの描画処理で決まるため、
ライセンス未認証の端末で検証してもハッシュは変わりません。「確認・確定した内容が
正しいか」という検証と、「出力にウォーターマークが入るか」という話を分離できます。

### 実際に検証したこと

実テンプレート・実データ（433件の明細行を含む帳票）を使い、以下をテストで確認済みです。

- 同一入力 → 完全に同一の manifest が返る（決定性）
- フォーマットだけ違う同一内容のJSON → `data_sha256` が一致する（正規化が機能）
- 明細行数を変える → `render_sha256` が変化し、`template_sha256` は変化しない

## まとめ

- AIに帳票デザインを書かせて確認・修正を繰り返すワークフローは、「プレビュー＝印刷結果」が
  保証されていて初めて、実機なしで成立する
- 「確認した」という事実を後から検証可能にするには、テンプレート・データ・描画結果・
  エンジン環境それぞれのハッシュを記録し、再描画して比較する仕組みが要る
- 描画結果のハッシュは最終PDFではなく中間描画命令に対して取ることで、環境差や
  メタデータの違いに左右されない再現性検証ができる
