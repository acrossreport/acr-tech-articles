# Puppeteer の PDF 生成でメモリ不足（OOM）になるときの根本対策

## これは何の話か

帳票・請求書・納品書などを Web システムから PDF 出力する際、多くの現場では Puppeteer（Headless Chrome）を使っていると思います。手軽に HTML/CSS で帳票レイアウトを組めるため導入は簡単なのですが、

- ページ数が数百〜数千枚になると急にメモリが膨らんで OOM Killed になる
- Docker コンテナのメモリ上限（512MB〜1GB）にすぐ張り付く
- 1 枚あたりの生成時間はそこそこでも、合計時間が線形以上に悪化していく

といった壁にぶつかった経験がある方は多いはずです。本記事では、まず Puppeteer で OOM が起きる構造的な理由を整理し、次に「そもそも Chrome を使わない」という選択肢――筆者が開発している Rust 製帳票エンジン ACR（Across Report）での実例――を紹介します。

## Puppeteer で OOM が起きる構造的な理由

Puppeteer / Headless Chrome で大量ページの PDF を生成するとき、メモリが膨らむ典型的な原因は次の4つに大別できます。

### 1. 数千ページ分の HTML を「1つのドキュメント」として丸ごと `page.pdf()` している

最も頻繁に踏む原因はこれです。帳票を1ページずつ別々に生成するのではなく、数百〜数千ページ分の `<div class="page">...</div>` を1つの巨大な HTML ドキュメントに連結し、最後に `page.pdf()` を1回呼ぶ実装をよく見かけます。この場合、Chrome はレイアウト計算・ペイント結果を「ページ全体のドキュメント」として一度にメモリ上に保持するため、ページ数に比例してメモリ使用量が線形以上に増えていきます。

有効な対策は、1リクエストで全ページを描画せず、**N ページ単位に分割して個別の PDF を生成し、`pdf-lib` や `qpdf` で後から結合する**ことです。分割生成であれば Chrome 側が一度に保持するレイアウトツリーのサイズを一定に抑えられます。

### 2. レンダラープロセスのヒープが「使い回し」を前提にしていない

Chrome のレンダラープロセスは本来「ページを開いて閉じる」ことを繰り返すために設計されており、1つの `page` オブジェクトで何百ページ分もの帳票を連続して `page.pdf()` し続けると、V8 のヒープや DOM ツリーのキャッシュが解放されずに蓄積していきます。`page.close()` / `browser.close()` のタイミングを誤ると、Node.js 側のプロセスにはゾンビの Chrome プロセスが残り続けることもあります。

### 2. フォント・画像リソースがページ単位で再読み込みされる

HTML/CSS ベースのレンダリングでは、`@font-face` で指定した日本語フォント（特にサブセット化されていないフォント）がページ遷移のたびに再パースされるケースがあります。帳票 1 枚ごとに同じフォントを何度も展開していると、ページ数に比例してメモリ使用量とレンダリング時間の両方が悪化します。

### 3. `page.pdf()` の出力バッファがプロセス内に溜まる

大量ページを1つの PDF にまとめる場合、Puppeteer 側でページごとの PDF バイト列をメモリ上で保持してから結合する実装になっていると、最終的な PDF サイズがそのまま Node.js プロセスのメモリ使用量に直結します。

## 対策の方向性（Puppeteer を使い続ける場合）

- 一定ページ数ごとに `browser` を再起動し、プロセスを使い捨てる
- フォントは Base64 埋め込みではなく、OS にインストール済みのフォントを `font-family` で直接参照させる
- 生成をワーカープロセスに分離し、OOM が起きてもメインプロセスに影響させない
- `--max-old-space-size` は Node.js（V8）側のヒープ上限を調整するフラグであり、Chrome のレンダラープロセスのメモリには効きません。レンダラー側のメモリを抑えたい場合は、前述の「ページ分割」や `browser` の定期再起動で対処する必要があります
- Docker のメモリ上限は、実際の帳票（想定される最大ページ数・画像枚数）で計測した Chrome の瞬間最大メモリに、十分なマージンを載せて決める（「3〜5倍」のような一般的な倍率はなく、コンテンツ次第で変動します）

ただし、これらは根本原因（「Chrome というブラウザエンジンを帳票レンダリングに転用している」こと自体）を回避する対症療法です。帳票の生成件数・ページ数が今後も増えていく前提であれば、別のアーキテクチャを検討する価値があります。

## もう一つの選択肢: ブラウザを使わない帳票レンダラー

筆者が開発している ACR（Across Report）は、HTML/CSS ではなく JSON テンプレートを中間描画モデル（`RenderCommand`）に変換し、Google Skia で直接 PDF/PNG を描画する Rust 製の帳票エンジンです。Chrome を介さないため、

- レンダラープロセスという概念自体がなく、V8 ヒープの蓄積問題が発生しない
- フォントはプロセス起動時に一度ロードしてキャッシュし、以降は参照のみ
- 生成した PDF はページ単位でストリーム書き込みされ、最終サイズがプロセスメモリに直結しない

という設計になっています。とはいえ「ブラウザを使わなければ自動的に安全」というわけではなく、実装次第では同種の問題を作り込んでしまいます。実際に筆者が踏んだ事例を紹介します。

## 実例: フォントの「ページ単位での再構築」が引き起こした肥大化

ACR の透かし（ウォーターマーク）描画処理 `draw_watermark()` は、当初ページを描画するたびに `FontMgr::new()` で新しい `Typeface` を解決していました。これは Puppeteer のフォント再パース問題とまったく同じ構造の不具合です。

結果として何が起きたかというと、PDF 出力ライブラリ（Skia の `SkPDF`）がページごとに別々のフォントサブセットを埋め込んでしまい、1,394 ページのサンプル帳票で

| | 修正前 | 修正後 |
|---|---|---|
| PDF サイズ | 約 300MB | 約 10.3MB |
| 生成時間 | 約 28秒 | 約 2.5秒 |

という差が出ました。修正は単純で、ページループの外側でフォントを 1 回だけ構築し、`draw_watermark()` にはその参照を渡すだけです（`font_cache` で既に使っていたのと同じパターンをウォーターマーク側にも適用した形です）。

なお、この数字は ACR 内での修正前後の比較であり、Puppeteer と同一帳票・同一データで直接比較したものではありません。本記事の主題である「Puppeteer の OOM」と並べて厳密な説得力を持たせるには、同じ帳票を Puppeteer と ACR の両方で生成し、メモリ使用量・生成時間を突き合わせたベンチマークが別途必要です。

この事例が示しているのは、「大量ページの帳票を生成するコードでは、"ページごとに毎回行っている処理" を疑うべき」という一般原則です。Puppeteer でも ACR でも、OOM やサイズ肥大化の多くはこの種の「本来 1 回で済むはずの初期化をループの中でやってしまっている」パターンに起因します。

## まとめ

- Puppeteer で大量ページの PDF 生成が重い・落ちるのは、Chrome のレンダラープロセスの性質上ある程度構造的な問題
- 対症療法（ブラウザ再起動・ワーカー分離・メモリ上限の調整）で凌ぐことはできるが限界がある
- 根本的に解決したい場合は、ブラウザエンジンを介さないネイティブレンダラーという選択肢もある
- ただしネイティブ実装でも「ページ単位での重複初期化」は同じ罠にはまるので、プロファイリングの観点は変わらない
